# Klyrow delivery-event synchronization release

Audit time: `2026-08-30T19:46:28Z`

## Incident boundary

The production Klyrow-to-Middleware transport is reachable, but the deployed
Server A receiver rejects delivery lifecycle events with HTTP 422
`unsupported_klyrow_event`. Klyrow held 329 provider events in its local DLQ
and the private integration gateway reported 122 Klyrow dead letters. No
customer message was generated by the connectivity tests.

The currently protected platform tuple points to Middleware source
`35448ef85ae56db3651a72b61db8e242b7aacd2e`. That source predates the durable
Klyrow delivery-event inbox merged in Codestra Middleware PR 262.

## Promotion and rollback controls

Use the protected production activation workflow in this order:

1. `preflight`
2. `backup`
3. `validate-backup`
4. `restore-test`
5. `stage` to pull and certify the exact Middleware image in an isolated
   standby container
6. `stage-control-plane` to validate and extract the exact protected platform
   archive containing the reviewed Middleware override
7. `validate-control-plane`
8. `rollout-middleware` to validate the captured ten-file production Compose
   graph, run Alembic through `0056_klyrow_delivery_events`, recreate only
   `middleware-integration-api`, `middleware-scheduler`, and
   `middleware-notification-worker`, and read back the exact running digest,
   health state, fail-closed flags, and database head
9. `activate-control-plane`; this action requires the exact-tuple
   `rollout-middleware` PASS record
10. `status`
11. `collect-evidence`

The protected release contains an updated restricted operator with only two
new verbs: `rollout-middleware` and `rollback-middleware`. Install that operator
from the signed protected release with the reviewed installer before step 1;
validate its pinned payload checksums, forced-command allowlist, sudoers file,
and installed tuple before allowing the workflow to connect. The rollout uses
the root/captured Compose paths and SHA-256 values in
`MIDDLEWARE_COMPOSE_LAYERS`; a changed, missing, linked, or writable layer is a
hard failure. Verified bytes are copied into an exact-release root-owned
directory before Docker Compose reads them. A retry preserves the original
rollback point, and rollback must read back every captured image ID before it
can record PASS. The rollback bundle also captures the pre-change Middleware
database, owner, Alembic head, checksum, and validated readiness-backup
reference; the selected stamp must equal the stamp recorded by `restore-test`.
Database dumps, validation, and restore input are streamed without buffering a
full dump in operator memory. Rollback stops the three replaced Middleware writers, preserves the
failed database state, disables new database connections before terminating all
remaining client sessions, and recreates the database with connection limit
zero. It restores the captured connection policy only after the pre-change dump
is fully restored and verifies the prior head. It never recreates PostgreSQL,
Redis, Odoo, Kong, or n8n.

Do not replay the production Klyrow DLQ during deployment. After activation,
submit one reserved `connectivity-audit` event, repeat its exact event ID to
prove replay protection, and confirm exactly one Middleware inbox row. Confirm
the approved downstream Odoo projection/readback before replaying any retained
event. Reprocess retained events in bounded batches with state and duplicate
counts recorded between batches.

Middleware rollback uses `rollback-middleware`, which restores the three
captured image IDs through the same checksum-bound Compose graph. Control-plane
rollback remains `rollback-control-plane`. Live email, SMS, PSTN, campaign, and
arbitrary Odoo write flags are outside this change and remain unchanged.
