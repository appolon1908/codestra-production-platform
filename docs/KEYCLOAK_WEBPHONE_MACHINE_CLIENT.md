# Canonical Keycloak webphone machine client

This document is the non-secret source authority for the machine identity used
by the canonical TEST_SYN webphone certification lane. It does not authorize a
production rollout or the use of staging credentials in production.

## Decision

The canonical client ID is `codestra-provisioning-service-staging`. The deployed
webphone issuer at middleware source revision
`80954a1ecb4eae49a57a9de245f78fd9a2f825a1` requests that exact client with the
`client_credentials` grant at the canonical `.co` token endpoint. The older
`codestra-client-provisioner` name is not consumed by that executable path, and
introducing a third client name would require an unapproved runtime change.

This client is confidential, service-account-only, and constrained to the
canonical TEST_SYN lane. Interactive standard, implicit, and direct password
grants are disabled. Full scope is disabled.

The executable posts the client ID and secret in the token request body, so its
OAuth client authentication method is `client_secret_post`; Keycloak represents
the corresponding confidential-client authenticator as `client-secret`.

## Executable claim contract

The private provisioning service verifies RS256 signature, issuer, audience,
`sub`, `exp`, `iat`, `jti`, `azp`, token type, and a scope string. It permits the
client ID in `azp`, rejects replayed `jti` values, and authorizes webphone routes
with exactly:

- `provisioning:execute` for session creation;
- `provisioning:read` for session configuration;
- `identity:rotate` for renewal and revocation.

The audience mapper therefore emits `codestra-provisioning-service`, and the
scope mapper emits only those three scopes. Access-token lifetime is capped at
300 seconds. No realm roles are assigned. The sole service-account client role
is `realm-management:view-users`, required by the webphone issuer's read-only
Admin API lookup of the already-authenticated browser subject. It does not
grant user mutation or client administration.

Tenant authority is not taken from the machine token. The webphone issuer first
validates the canonical browser token and then verifies subject, tenant,
campaign, and extension through the Odoo identity lookup. The allowlist in
`config/keycloak-webphone-allowed-tenants.json` makes the certification boundary
explicit; no tenant protocol mapper is required by the executable verifier.

## Environment separation

`config/keycloak-staging-contract.env.example` remains the internal staging
contract and is not modified. Its issuer, audience, secret, and delivery policy
remain separate. This canonical client is also not the production middleware
identity defined by `config/keycloak-production-contract.env.example`.

The canonical secret is generated by Keycloak and mounted only at
`/run/secrets/provisioning/client_secret`. It is never committed. Delivery must
use the established origin-held SSH key, forced exporter, fingerprint-checked
stdin installer, and atomic replacement pattern.

## Known runtime drift and activation gate

At the time this contract was published, the running provisioning verifier
still declared the legacy issuer `https://auth.codestra.agency/realms/codestra`.
That is deployment drift, not authority for this client. Before creating or
using the client, a separate approved runtime mission must reconcile the
verifier to `https://auth.codestra.co/realms/codestra`, rebuild/release its
immutable image if required, and prove the token contract end to end. This
contract alone changes no runtime, Keycloak, or telephony state.
